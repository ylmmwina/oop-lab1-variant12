# Пояснення лабораторної та підготовка до захисту

## Завдання

Варіант 12 — «Мобільний зв’язок». Потрібно створити ієрархію тарифів, список тарифів компанії, підрахувати загальну кількість клієнтів, відсортувати тарифи за абонплатою та знайти тарифи за діапазоном параметрів. Загальні вимоги: ООП, пакети, мінімальна консоль, JUnit і Mockito, Git та віддалений репозиторій.

## Як побудовано програму

`Tariff` — абстрактний клас, який описує назву, місячну плату, кількість клієнтів, хвилини та ГБ. Сам по собі загальний тариф не створюємо: створюємо один із конкретних типів. Конструктор базового класу перевіряє спільні дані.

`VoiceTariff` має хвилини й нуль ГБ, `DataTariff` має ГБ і нуль хвилин, `CombinedTariff` має обидва пакети. Кожен перевизначає `getType()` та повертає свою назву типу. Таке успадкування змістовне: кожен із цих об’єктів є тарифом.

`MobileCompany` містить тарифи через композицію. Компанія не є тарифом, тому не успадковує його. Конструктор копіює переданий список. Метод `getTariffs()` повертає незмінну копію, тому зовнішній код не може непомітно змінити внутрішній список.

`TariffCriteria` зберігає шість меж пошуку: мінімальну й максимальну плату, хвилини, ГБ. Його метод `matches()` повертає `true`, тільки коли тариф задовольняє всі три включні діапазони.

`Main` створює навчальні дані, викликає методи компанії та виводить результати. Бізнес-операції винесені з консолі, тому їх можна перевірити незалежно від виведення.

## Де саме ООП

- Абстракція: `Tariff` описує спільну модель без прив’язки до конкретного виду.
- Інкапсуляція: `private final` поля, перевірки в конструкторах, відсутність setter-методів і захисні копії колекцій.
- Успадкування: три класи тарифів `extends Tariff`.
- Поліморфізм: усі тарифи лежать у `List<Tariff>`. Під час `tariff.getType()` Java викликає реалізацію фактичного типу об’єкта.

`final` у посиланні на список забороняє замінити саме посилання, але не забороняє сортувати його вміст. Незмінність зовнішнього представлення забезпечується `List.copyOf()`.

## Результати і розрахунки

Навчальні тарифи:

| Тариф | Плата, грн/місяць | Клієнти | Хвилини | Інтернет, ГБ |
| --- | ---: | ---: | ---: | ---: |
| Максимум | 450.00 | 800 | 1000 | 50 |
| Розмова | 120.00 | 1200 | 300 | 0 |
| Онлайн | 200.00 | 600 | 0 | 40 |
| Баланс | 250.00 | 1500 | 500 | 20 |

Підрахунок клієнтів: 800 + 1200 = 2000; 2000 + 600 = 2600; 2600 + 1500 = **4100 клієнтів**. Припускаємо, що кожен клієнт належить одному тарифу. Використано `long`, щоб сума не переповнила `int` для великих кількостей.

Сортування за зростанням: **Розмова (120.00) → Онлайн (200.00) → Баланс (250.00) → Максимум (450.00 грн/місяць)**. Для однакової плати зберігається початковий взаємний порядок.

Пошук: 200 ≤ плата ≤ 300 грн/місяць; 0 ≤ хвилини ≤ 600; 20 ≤ ГБ ≤ 40. «Онлайн» відповідає нижній межі ціни та верхній межі інтернету, «Баланс» також відповідає всім умовам. «Розмова» має замалу плату і немає пакета інтернету, «Максимум» перевищує межі. Результат: **Онлайн, Баланс**.

Для грошей `BigDecimal` зберігає точне десяткове значення. `setScale(2, UNNECESSARY)` додає нулі, але забороняє приховане округлення дробових копійок. Порівнюємо через `compareTo`, щоб `9` та `9.00` мали однакове числове значення.

## Алгоритми

Підрахунок: stream перетворює кожен тариф у кількість клієнтів типу `long` і підсумовує. Час O(n).

Сортування: `Comparator.comparing(Tariff::getMonthlyFee)` задає ключ порівняння; `List.sort` змінює внутрішній порядок. Типова верхня оцінка часу O(n log n).

Пошук: `filter(criteria::matches)` перевіряє кожен тариф і повертає незмінний список результатів. Час O(n), додаткова пам’ять O(k), де k — кількість знайдених тарифів.

## Що перевіряють тести

`TariffTest` перевіряє дані кожного підкласу, поліморфізм, порожні назви, null, від’ємні числа, нуль та дробові копійки.

`TariffCriteriaTest` перевіряє попадання в діапазон, точні межі й значення одразу за кожною межею, неправильний порядок меж і null.

`MobileCompanyTest` перевіряє суму, стабільне числове сортування, порожню компанію, усі результати пошуку, відсутність результатів та захист колекцій. Mockito створює два об’єкти-підміни `Tariff`: `when(...).thenReturn(...)` задає кількість клієнтів, а `verify(...)` перевіряє звернення компанії до кожного тарифу. Тест суми 2147483647 + 10 = **2147483657** перевіряє використання `long`.

`MainTest` порівнює весь демонстраційний вивід з очікуваним текстом і перевіряє точку входу. Приватний конструктор перевірено окремо. JaCoCo вимірює покриття рядків і гілок; `verify` відхиляє збірку, якщо хоча б одна з цих метрик менша за 100%.

## Коротка розповідь для захисту

«У цій лабораторній я реалізувала варіант 12 — мобільну компанію. Базовий абстрактний клас Tariff містить спільні характеристики. Від нього успадковані голосовий, інтернетний і комбінований тарифи. Усі вони зберігаються в одному списку List<Tariff>, а метод getType демонструє поліморфізм.

Компанія має три основні операції: підрахунок клієнтів, сортування за місячною платою і пошук за включними діапазонами плати, хвилин та інтернету. На навчальних даних отримуємо 4100 клієнтів. Після сортування плата зростає від 120 до 450 гривень. За заданими критеріями пошуку підходять Онлайн і Баланс.

Поля тарифів приватні й незмінні, а списки захищені копіями. Для грошей використано BigDecimal. Коректність перевіряють JUnit-тести, а Mockito ізолює перевірку підрахунку клієнтів. Проєкт збирається Maven на Java 25».
